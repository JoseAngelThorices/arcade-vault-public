## Project

**Arcade Vault** — an online gaming platform where players compete for high scores (see `README.md`). The Next.js side is still at the scaffold stage: a single App Router route (`app/page.tsx`) with the default create-next-app content, and `app/layout.tsx` metadata still reads "Create Next App". There is no game, data layer, or API yet, so most work means adding new structure rather than modifying existing code.

The product itself is already designed: `references/templates/` holds a complete, working prototype of the whole app (see below). Treat it as the functional and visual spec for what gets built in `app/`.

The README states the project follows Spec Driven Design via the `/spec` and `/spec-impl` skills from `Klerith/fernando-skills` (installed with `npx skills@latest add Klerith/fernando-skills`). Those skills are not installed in this environment; if a spec-first workflow is expected, ask the user before implementing features directly.

## The prototype in `references/templates/`

A standalone, no-build prototype — open `Arcade Vault.html` directly in a browser. It is **not** part of the Next.js build and shares no code with `app/`.

How it works, and why it differs from the target stack:

- `Arcade Vault.html` loads React 18 UMD + `@babel/standalone` from unpkg and pulls each `.jsx` file as `<script type="text/babel">`. There are no imports/exports: every component is a global, so **script order in the HTML is the dependency graph** (`data.jsx` → screens → `app.jsx` last, which calls `ReactDOM.createRoot`). `data.jsx` publishes `window.GAMES`, `window.CATS`, `window.seededScores`.
- Each screen file destructures React hooks under a unique alias (`useStateApp`, `useStateP`, `useStateB`, …) purely to avoid global collisions — an artifact of the UMD setup, not a pattern to carry into `app/`.
- Routing is hand-rolled in `app.jsx`: route state is an object (`{ name, id }`) serialized into `location.hash`, with `navigate(route)` passed down as a prop. Screens: `biblioteca` (library grid), `detalle` (game detail), `player` (in-game HUD), `auth`, `salon` (hall of fame).
- "Persistence" is `localStorage` only: `av_user` (session) and `av_scores` (score log). Auth in `auth.jsx` accepts anything and fabricates a user. Scores in `salon.jsx` come from `seededScores()`, a deterministic LCG over a fixed `PLAYERS` list — mock data, not a backend.
- `reproductor.jsx` does not run real games: a `setInterval` increments the score to simulate play. The nine entries in `GAMES` are metadata and cover art only.
- `styles.css` (~950 lines, plain CSS, no Tailwind) carries the design language: neon tokens on `:root` (`--cyan #00f5ff`, `--magenta #ff006e`, `--bg #0a0a0f`, …), `--pixel` = Press Start 2P and `--mono` = JetBrains Mono from Google Fonts, plus CRT/scanline/perspective-grid effects and per-game gradient covers (`cover-bricks`, `cover-snake`, …).

When porting a screen: keep the layout, copy, and visual tokens; re-derive the code. The target is React 19 + Server Components + Tailwind v4, where the prototype's globals, prop-drilled router, and plain CSS do not apply. The neon `:root` tokens belong in `@theme inline` in `app/globals.css`.

All UI copy is in Spanish, and numbers are formatted with `toLocaleString("es-ES")`. Keep new UI text Spanish.

## Stack notes that differ from older Next.js

This is **Next.js 16.3.5** with React 19.2 and Tailwind CSS v4. `AGENTS.md` (imported above) is authoritative: read the relevant page under `node_modules/next/dist/docs/` before writing framework code. Key differences from pre-16 knowledge:

- **Turbopack is the default** for both `dev` and `build`; the `--turbopack` flag is obsolete. Turbopack options live under `turbopack` in `next.config.ts`, not `webpack`. A `webpack` config makes `next build` fail unless run with `--webpack`.
- **Request APIs are async-only.** `cookies()`, `headers()`, `draftMode()`, and `params`/`searchParams` must be awaited; synchronous access was removed, not just deprecated.
- **Global route-type helpers.** `PageProps<'/route'>`, `LayoutProps<'/route'>`, and `RouteContext<'/route'>` are globally available and generated by `next typegen`; they are not imported. `app/layout.tsx` already uses `LayoutProps<"/">`.
- **`middleware.ts` is now `proxy.ts`** — the old convention is deprecated.
- **`next lint` is gone.** Linting runs through the ESLint CLI with `eslint.config.mjs` (flat config, `eslint-config-next/core-web-vitals` + `/typescript`).
- PPR's `experimental_ppr` segment config and `unstable_` prefixes on stabilized APIs were removed. Caching uses `revalidateTag`/`updateTag`/`refresh` and `cacheLife`/`cacheTag`.
- Several `next/image` defaults changed (`minimumCacheTTL`, `imageSizes`, `qualities`, local images with query strings, local IP restriction) — check `node_modules/next/dist/docs/01-app/02-guides/upgrading/version-16.md` before tuning image config.

## Conventions

- TypeScript is `strict`, path alias `@/*` maps to the repo root. `allowJs` is on and `include` is broad, so the prototype's `.jsx` files are inside the TS program — do not add type-aware tooling that would try to check them.
- Tailwind v4 is configured through PostCSS (`postcss.config.mjs`) with no `tailwind.config` file; theme tokens are declared in `app/globals.css` using `@theme inline` and CSS variables (`--background`, `--foreground`, Geist font variables set in `app/layout.tsx`).
- `AGENTS.md` is regenerated by `next dev`. If it shows up as an uncommitted change, commit it with the work instead of reverting it.
- The git repository root is the user's home directory, not this folder — `git status` without a path shows unrelated home-directory noise. Scope git commands to this directory (`git status .`, `git add .`).
